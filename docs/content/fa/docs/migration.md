> **جابه‌جا کردن سرور همان جایی است که پیکربندی‌ها گم می‌شوند.**
> گونیکس سه راه برای این کار دارد، و همه را می‌شود با `--dry-run` شروع کرد.

## رفتن به سرور جدید

همه‌چیزهایی را که گونیکس مدیریت می‌کند در یک آرشیو بگیرید و روی سرور دیگر وارد کنید.

```bash
sudo gonix export gonix-backup.tar.gz                 # روی سرور قدیمی
sudo gonix import gonix-backup.tar.gz --dry-run       # روی سرور جدید: ببینید چه چیزی تغییر می‌کند
sudo gonix import gonix-backup.tar.gz
```

- اگر به‌جای نام فایل `-` بگذارید، خروجی روی stdout می‌آید (مثلاً برای انتقال مستقیم با SSH).
- import فایل‌های موجود را بازنویسی نمی‌کند، مگر اینکه `--overwrite --yes` بدهید.

{{< callout type="info" >}}
**چرا import را با dry-run امتحان کنیم؟** import بزرگ‌ترین تغییری است که با یک دستور می‌شود داد. دیدن diff ده ثانیه وقت می‌گیرد و
می‌تواند یک شب کار را نجات بدهد.
{{< /callout >}}

## خداحافظی با Nginx Proxy Manager

> **باید سی هاست را دوباره دستی بسازید؟**
> نه. کافی است گونیکس را به پوشه‌ی داده‌های NPM راهنمایی کنید.

```bash
sudo gonix npm-import --data /opt/npm/data --letsencrypt /opt/npm/letsencrypt --dry-run
```

هاست‌های پروکسی، ریدایرکت‌ها، streamها، گواهی‌ها و لیست‌های دسترسی منتقل می‌شوند. اگر `--disabled` را بدهید، هاست‌ها وارد می‌شوند اما فعال
نمی‌شوند؛ شروع خوبی است: اول ببینید، بعد یکی‌یکی فعال کنید.

هر چیزی که قابل تبدیل نباشد (پیکربندی پیشرفته‌ی سفارشی یا هاست‌هایی که فقط wildcard دارند) **گزارش می‌شود، نه اینکه حدس زده شود**. یک
حدس اشتباه که بی‌سروصدا وارد پیکربندی پروکسی شود، از یک جای خالی که معلوم است بدتر است.

## Adopt کردن هاست‌های دست‌نویس (و certbot)

> **برای استفاده از گونیکس باید سایت‌هایی را که دستی تنظیم کرده‌اید از نو بنویسید، یا certbot را کنار بگذارید؟**
> نه. آن‌ها را adopt کنید: گونیکس فایل را همان‌طور که هست تحویل می‌گیرد.

```bash
sudo gonix adopt example.com --dry-run    # گونیکس چه چیزی از فایل می‌خواند، و همان تغییر یک‌خطی
sudo gonix adopt example.com              # یا: sudo gonix adopt --all
```

adopt کردن فقط **یک کامنت** به بالای فایل اضافه می‌کند (`# Adopted by GoNix. ...`) و هیچ چیز دیگری را عوض نمی‌کند؛ پس Nginx دقیقاً
همان پیکربندی قبلی را سرو می‌کند. از این به بعد هاست managed است: تنظیماتش را می‌شود از TUI، CLI یا یک عامل هوش مصنوعی تغییر داد، و هر
تغییر **فقط دستورهای مربوط به خودش را ویرایش می‌کند**. کامنت‌ها، ترتیب خطوط و هر دستوری که گونیکس برایش تنظیمی ندارد (`try_files`،
`fastcgi_pass`، `add_header`، خطوط خود certbot و ...) دقیقاً همان‌طور که نوشته‌اید می‌مانند.

گونیکس این‌ها را از فایل می‌خواند:

- نام‌های سرور، پورت‌های listen، گواهی SSL، HTTP/2 و ریدایرکت HTTP به HTTPS؛
- یک `root`، یا یک `return 301 ...` در سطح server (هاست ریدایرکت)؛
- **locationهایی که فقط یک reverse proxy ساده‌اند** (`proxy_pass http://host:port` به‌همراه هدرها و timeoutهای معمول)؛ بقیه‌ی
  locationها به‌عنوان **location سفارشی**، دقیقاً همان‌طور که نوشته شده‌اند، نگه داشته می‌شوند؛
- snippetهایی که خود گونیکس بعداً اضافه می‌کند: presetها، لیست‌های IP، محدودیت نرخ، لیست کشورها، لیست‌های Basic Auth، صفحه‌های خطا
  و حالت تعمیر.

گزارش adopt هر چیزی را که **همان‌طور که نوشته شده نگه داشته می‌شود** فهرست می‌کند، تا ببینید گونیکس به چه چیزهایی هرگز دست نمی‌زند.

برای اینکه همه‌ی این‌ها را اول روی تنظیمات دست‌نویس و certbot رایج امتحان کنید، از [آزمایشگاه]({{< relref "lab" >}}) استفاده کنید.

**چه فایل‌هایی adopt می‌شوند:** فایلی با یک بلاک `server`، و در صورت وجود، بلاک HTTP ساده‌ای که آن را به HTTPS ریدایرکت می‌کند (همان
ساختاری که `certbot --nginx` می‌نویسد). اولین نام در `server_name` باید یک دامنه‌ی معمولی باشد؛ wildcard و نام‌های دیگر بعد از آن
مشکلی ندارند. هر فایل دیگری با ذکر دلیل رد می‌شود و `[unmanaged]` می‌ماند.

**هر تغییر قبل از نوشته شدن بررسی می‌شود.** گونیکس بعد از ویرایش، فایل را دوباره می‌خواند؛ اگر نتیجه دقیقاً همان هاستی نباشد که
خواسته‌اید، تغییر رد می‌شود، نه اینکه نیمه‌کاره نوشته شود. بعد همان مسیر همیشگی طی می‌شود: بکاپ، `nginx -t`، reload یا rollback. فایلی
که بعد از خوانده شدن توسط گونیکس دستی ویرایش شده باشد هرگز بازنویسی نمی‌شود.

بعضی تغییرها روی هاست‌های adopt‌شده رد می‌شوند و پیامش را می‌بینید: تغییر نام هاست، تغییر پورت‌های listen، خاموش کردن SSL، HTTP/3،
و تغییر ریدایرکت HTTP به HTTPS وقتی در یک بلاک server جداگانه است. این‌ها را دستی انجام دهید.

### گواهی‌های certbot

adopt کردن هیچ‌وقت به گواهی‌ها دست نمی‌زند. هاستی که از `/etc/letsencrypt/live/<name>/fullchain.pem` استفاده می‌کند، همچنان از
همان استفاده می‌کند، و **certbot مثل قبل با تایمر خودش آن را تمدید می‌کند**. گونیکس این گواهی‌ها را تشخیص می‌دهد (`gonix host show`
و `gonix cert list` آن‌ها را متعلق به certbot نشان می‌دهند) و تنظیمات تمدید certbot را می‌خواند تا درباره‌ی پیش‌نیازهای تمدید هشدار
بدهد؛ مثلاً با authenticator `nginx` در certbot، هاست باید همچنان روی پورت ۸۰ به HTTP ساده جواب بدهد.

```bash
sudo gonix adopt example.com --verify-renewal   # certbot renew --dry-run را هم برای گواهی‌اش اجرا می‌کند
```

هر وقت خواستید گواهی را به گونیکس بسپارید، آن را در پوشه‌ی گواهی‌ها بگذارید (به [گواهی‌های SSL]({{< relref "ssl" >}}) نگاه کنید) و
هاست را به آن منتقل کنید. فقط دو خط گواهی عوض می‌شوند؛ HTTP/2 و ریدایرکت همان‌طور که بودند می‌مانند:

```bash
sudo gonix host set example.com --ssl example.com
```

certbot تا وقتی گواهی قدیمی را حذف نکنید (`certbot delete --cert-name example.com`) به تمدید آن ادامه می‌دهد؛ گونیکس هیچ‌وقت این کار
را به‌جای شما انجام نمی‌دهد.

### پس دادن یک هاست

```bash
sudo gonix adopt release example.com
```

علامت را برمی‌دارد. فایل همه‌ی تغییرهایی را که در مدت مدیریت گونیکس انجام شده نگه می‌دارد و دوباره `[unmanaged]` می‌شود.
