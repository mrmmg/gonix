> **چطور گونیکس را روی پیکربندی دست‌نویس امتحان کنیم، بی‌آنکه سرور واقعی به خطر بیفتد؟**
> در آزمایشگاه: یک Nginx دوم و جدا از Nginx سیستم، که گونیکس خودش راه‌اندازی می‌کند و برایتان با هاست‌های آزمایشی پر می‌کند.

آزمایشگاه تا وقتی نخواهید پنهان است:

```bash
sudo GONIX_LAB=1 gonix
```

در این حالت گزینه‌ی **Lab** در منوی اصلی ظاهر می‌شود. بدون `GONIX_LAB` وجود ندارد.

## آزمایشگاه چیست

| بخش | کجا |
|---|---|
| پیکربندی Nginx | پوشه‌ی آزمایشگاه (پیش‌فرض `/srv/gonix-lab`)، با `nginx.conf`، `sites-available`، `sites-enabled`، لاگ‌ها و گواهی‌های خودش |
| پروسه‌ی Nginx | systemd unit به نام `gonix-lab`، به‌طور پیش‌فرض روی پورت‌های **8080** (HTTP) و **8443** (HTTPS) |
| backendها برای پروکسی | `127.0.0.1:19001` جواب «backend A» و `127.0.0.1:19002` جواب «backend B» می‌دهد |
| نگاه گونیکس به آن | یک [نمونه]({{< relref "instances" >}}) به نام `lab` (`/etc/gonix/instances/lab.yaml`)، با بکاپ، تاریخچه و audit log جدا |

به `/etc/nginx` و `nginx.service` هیچ‌وقت دست زده نمی‌شود، و Nginx سیستم می‌تواند هم‌زمان روشن بماند.

## منوی Lab

- **Set Up Lab:** پوشه و دو پورت را می‌پرسد، و اینکه از هر نوع یک هاست آزمایشی ساخته شود یا نه. پوشه باید جدید یا خالی باشد.
- **Enter Lab:** کل TUI را به آزمایشگاه می‌برد. نوار عنوان `lab` را نشان می‌دهد، منوی اصلی یک خط قرمز **LAB** دارد، و همه‌ی صفحه‌ها
  روی Nginx آزمایشگاه کار می‌کنند. **Exit Lab** (یا Esc) برمی‌گرداند.
- **Add Test Host:** یک هاست دست‌نویس از نوعی که انتخاب می‌کنید می‌نویسد، فعالش می‌کند و با `nginx -t` بررسی‌اش می‌کند (هاستی که رد
  شود دوباره حذف می‌شود).
- **Start / Stop Lab Nginx**، **Reset Lab** (شروع دوباره)، **Remove Lab** (unit را متوقف می‌کند و پوشه، فایل unit و نمونه را پاک می‌کند).
- **Usage Guide:** مسیرهای آزمایشگاه، دستورهای استفاده از آن در shell، و پیشنهاد سناریوهای تست. تمام ارتفاع ترمینال را پر
  می‌کند و با `PgUp` / `PgDn` صفحه‌به‌صفحه جابه‌جا می‌شود.

## هاست‌های آزمایشی

هر نوع، الگویی است که روی سرورهای واقعی پیدا می‌شود، و هر کدام بخش متفاوتی از
[adopt کردن]({{< relref "migration#adopt-کردن-هاستهای-دستنویس-و-certbot" >}}) را امتحان می‌کند:

| نوع | دامنه‌ی پیشنهادی | adopt کردنش چه چیزی را نشان می‌دهد |
|---|---|---|
| reverse proxy بعد از `certbot --nginx` | `app.lab.test` | گواهی و بلاک HTTP مربوط به certbot، و یک location سفارشی |
| reverse proxy ساده | `api.lab.test` | دستوری که همان‌طور که نوشته شده می‌ماند |
| سایت static با `try_files` | `static.lab.test` | هاست static، با حفظ تورفتگی tab |
| ریدایرکت کل دامنه | `old.lab.test` | هاست ریدایرکت |
| نام wildcard | `wild.lab.test` | نام `*.` که همچنان کار می‌کند |
| locationهای PHP، نام‌دار و WebSocket | `php.lab.test` | locationهای سفارشی کنار یک پروکسی |
| دو سایت در یک فایل | `multi.lab.test` | رد شدن: دو بلاک server |
| default server همه‌گیر | | رد شدن: `server_name _` |

هاست certbot یک پوشه‌ی certbot شبیه‌سازی‌شده دارد (`<lab>/letsencrypt` به‌همراه فایل renewal)، تا گونیکس گواهی‌اش را متعلق به certbot
بداند، و یک نسخه از گواهی هم در پوشه‌ی گواهی‌های آزمایشگاه هست تا بتوانید هاست را
[به آن منتقل کنید]({{< relref "migration#گواهیهای-certbot" >}}). گواهی‌ها self-signed هستند.

## استفاده از shell

آزمایشگاه یک نمونه‌ی معمولی است:

```bash
sudo gonix --instance lab host list
sudo gonix --instance lab adopt --all --dry-run
sudo gonix --instance lab history show <commit>     # diff دقیق یک تغییر
```

برای فرستادن درخواست به دامنه‌های آزمایشی بدون ویرایش `/etc/hosts`:

```bash
t() { local h=${1#*://}; h=${h%%/*}; h=${h%%:*}
      curl -sk -i --resolve "$h:8080:127.0.0.1" --resolve "$h:8443:127.0.0.1" "$@"; }
t http://app.lab.test:8080/
t https://app.lab.test:8443/
```

{{< callout type="info" >}}
**چرا پورت‌های دیگر؟** تا آزمایشگاه هیچ‌وقت سر پورت‌های 80 و 443 با Nginx سیستم رقابت نکند. وقتی HTTPS روی 443 نباشد (تنظیم
`https_port`)، گونیکس شماره‌ی پورت را در ریدایرکت‌های HTTP به HTTPS که می‌نویسد می‌گذارد، پس ریدایرکت‌ها در آزمایشگاه هم درست کار می‌کنند.
{{< /callout >}}

`adopt --verify-renewal` در آزمایشگاه شکست می‌خورد، چون گواهی‌های certbot آن شبیه‌سازی‌شده‌اند.
