# GoNix — Ideas & Roadmap

A working list of features that could make GoNix a more complete Nginx management tool, ordered
by suggested priority (value to users vs. implementation cost). Nothing here is committed to yet;
it is a place to think before building.

## Implementation status

Everything below is implemented on `feat/next-release`, with unit tests, TUI tests and (when
`nginx` is installed) real `nginx -t` and behavioural tests:

| Idea | Status |
| --- | --- |
| IP allow/deny lists, `satisfy`, real client IP | Done (TUI + CLI) |
| Host presets (headers, HSTS, gzip, static cache, proxy cache, sensitive files, bad bots) | Done |
| Rate limiting presets | Done |
| Redirect hosts, domain aliases, maintenance mode | Done |
| Live log viewer with filters, summary and "block IP" | Done |
| Config Check (lint) and upstream health | Done |
| Upstream groups & load balancing | Done (passive health checks only) |
| Stream (TCP/UDP) proxy | Done (needs the stream module) |
| GeoIP country blocking | Done (needs the geoip2 module) |
| HTTP/2 syntax per Nginx version, HTTP/3 | Done |
| OCSP stapling | Skipped — Let's Encrypt shut down its OCSP responders in 2025 |
| Git configuration history, export/import, NPM import | Done |
| Multiple Nginx instances | Done |
| CLI with `--json`/`--dry-run`, agent skill, MCP server | Done |

## Guiding principle

Every feature below should follow the same rule GoNix already follows for access lists and error
pages: **generate a named, reusable, human-readable snippet** (under `snippets/` or `conf.d/`) and
attach it to a host or location with a plain `include`. Settings should not be scattered inline
through host files. Someone opening `/etc/nginx/sites-available/example.com` should immediately
see what is attached and where it lives.

Every change also goes through the existing safety pipeline: backup → write → `nginx -t` →
reload, or automatic rollback.

## Priority 1 — IP allow/deny lists (with `satisfy` and real client IP)

### What

Named, reusable IP access lists that can be applied to a host or a single location, exactly like
the existing Basic Auth access lists.

```nginx
# /etc/nginx/snippets/gonix-ip-office.conf  (generated by GoNix)
allow 192.168.1.0/24;
allow 10.0.0.5;
deny all;
```

```nginx
location /admin/ {
    include /etc/nginx/snippets/gonix-ip-office.conf;
    proxy_pass http://127.0.0.1:8080;
}
```

### Combining with Basic Auth: `satisfy`

When a host has both an IP list and a Basic Auth list, the user should choose how they combine:

```nginx
satisfy any;   # allowed IP  OR  valid username/password
# satisfy all; # allowed IP  AND valid username/password
```

`satisfy any` is very useful in practice: no password prompt from the office network, but a
password is required from anywhere else.

### Real client IP (critical)

If Nginx sits behind Cloudflare or another load balancer, `$remote_addr` is the proxy's IP, not
the client's. Every allow/deny rule then silently matches the wrong address. GoNix should offer a
"Behind a proxy / CDN" option that generates:

```nginx
# /etc/nginx/conf.d/gonix-realip.conf
set_real_ip_from 173.245.48.0/20;   # Cloudflare ranges (fetched/updated by GoNix)
set_real_ip_from 103.21.244.0/22;
# ...
real_ip_header CF-Connecting-IP;    # or X-Forwarded-For for a generic LB
real_ip_recursive on;
```

A built-in "Cloudflare" preset that fetches the published IP ranges would remove one of the most
common Nginx pitfalls.

### Notes

- Validate every entry as an IP or CIDR (`net.ParseIP` / `net.ParseCIDR`).
- Show which hosts and locations use each list, as access lists already do.
- Rule order matters in Nginx (first match wins), so the UI should keep entries ordered and
  allow reordering.

## Priority 2 — One-click host presets

Cheap to implement, very visible to new users. Each one is a toggle on the host screen that
includes a shared snippet.

| Preset | What it adds |
|---|---|
| **Force HTTPS** | A port 80 server block that returns `301 https://$host$request_uri` |
| **HSTS** | `Strict-Transport-Security` (with a clear warning before enabling `preload`) |
| **Security headers** | `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` |
| **Compression** | gzip, plus brotli if the module is detected |
| **Static asset caching** | `expires` / `Cache-Control` for css, js, images and fonts |
| **HTTP/2, HTTP/3** | Enabled only if the installed Nginx version supports it |
| **OCSP stapling** | `ssl_stapling on; ssl_stapling_verify on;` plus a resolver |

Example (security headers snippet):

```nginx
# /etc/nginx/snippets/gonix-security-headers.conf
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
```

Note: `add_header` directives in a `location` replace all inherited ones from the `server`
level. GoNix should handle this when a location adds its own headers, or at least warn about it.

## Priority 3 — Rate limiting presets

Rate limiting is split across two contexts, which is why it confuses people:

1. The zone is declared once in the `http` context:

   ```nginx
   # /etc/nginx/conf.d/gonix-ratelimit.conf
   limit_req_zone $binary_remote_addr zone=gonix_api:10m   rate=10r/s;
   limit_req_zone $binary_remote_addr zone=gonix_login:10m rate=5r/m;
   limit_conn_zone $binary_remote_addr zone=gonix_conn:10m;
   limit_req_status 429;
   limit_conn_status 429;
   ```

2. It is applied in a server or location:

   ```nginx
   location /api/ {
       limit_req zone=gonix_api burst=20 nodelay;
       limit_conn gonix_conn 20;
       proxy_pass http://127.0.0.1:3000;
   }
   ```

GoNix should hide this split. The user picks a named preset (e.g. *API: 10 r/s, burst 20*,
*Login: 5 r/min*, *Strict*) or creates a custom one, and GoNix manages both files. This depends
on the real-IP setting from Priority 1, otherwise every client shares the proxy's bucket.

## Priority 4 — Redirect hosts & maintenance mode

### Redirect host

A new host type that only redirects. It covers `www` → apex, old domain → new domain, and similar
cases:

```nginx
server {
    listen 80;
    listen 443 ssl;
    server_name old-example.com www.old-example.com;
    # ssl_certificate ...
    return 301 https://example.com$request_uri;
}
```

Options: 301/302/307/308, and whether to preserve the path and query string.

**Current workaround (before this exists).** Today GoNix only has `Reverse Proxy` and
`Direct / Static` modes, and the only built-in redirect is *Force HTTPS* (same domain). A
cross-domain redirect can be built from existing pieces:

1. Add a `Direct / Static` host for `domain.net` (any root, it is never served).
2. Enable SSL for it (a certificate for `domain.net` itself is required for HTTPS).
3. Add a custom location `/` containing `return 301 https://domain.com$request_uri;`.

Limitations: HTTP requests take two hops when *Force HTTPS* is on, only `/` is covered, the
wizard cannot add `www.domain.net` as an alias, and the root field is meaningless.

**Planned design.** A third host mode, `Redirect`, with:

- target URL/domain (validated), redirect code (301/302/307/308, default 301),
- "preserve path and query" toggle (`$request_uri`), on by default,
- aliases (`www.domain.net`), which also fixes the missing alias support in the wizard,
- optional SSL, with a single `return` at server level (no root, no locations), so HTTP and
  HTTPS both go straight to the target in one hop.

Touches `nginx.HostMode`, `Host.Validate`, `host.tmpl`, the parser (round-trip of the new
mode) and the add-host wizard; renderer and parser get round-trip tests.

### Maintenance mode

A per-host toggle that returns 503 with a custom page while letting admin IPs through. It reuses
both the IP lists (Priority 1) and the error pages GoNix already has:

```nginx
# included while maintenance mode is on
geo $gonix_maint_bypass {
    default 0;
    192.168.1.0/24 1;
}
```

```nginx
location / {
    if ($gonix_maint_bypass = 0) { return 503; }
    proxy_pass http://127.0.0.1:3000;
}
error_page 503 /gonix-maintenance.html;
```

(`geo` must live in the `http` context, so it goes in `conf.d/`, as with rate limiting.)

## Priority 5 — Live log viewer with actions

This is where a TUI can beat a web panel, and it could be GoNix's distinguishing feature.

- Tail a host's access/error log live, with filters: status code (`5xx`), client IP, path,
  method.
- A quick summary view: top IPs, top paths, 4xx/5xx counts, requests per minute.
- **Act from the log:** select a line → "Block this IP" (adds it to an IP deny list from
  Priority 1) or "Rate-limit this path".

Example summary screen:

```text
example.com — last 5 minutes
  Requests: 12,430   2xx 96.1%   4xx 3.2%   5xx 0.7%
  Top IPs:   203.0.113.7 (4,210)   198.51.100.2 (880)
  Top 5xx:   /api/upload (61)
  [b] Block selected IP   [r] Rate-limit path   [/] Filter
```

Related low-cost additions:

- **Upstream health check:** a TCP dial to each host's backend, shown as ● up / ○ down in the
  host list.
- **Certificate expiry warnings** on the main dashboard.
- **Config lint:** duplicate `server_name` across hosts, SSL hosts with no HTTP→HTTPS redirect,
  locations whose `add_header` drops inherited security headers, unused access lists.

## Priority 6 — Bigger features

### Upstream groups & load balancing

```nginx
upstream gonix_app {
    least_conn;
    server 10.0.0.11:3000 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:3000 max_fails=3 fail_timeout=10s;
    server 10.0.0.13:3000 backup;
}

location / {
    proxy_pass http://gonix_app;
}
```

Options: `round_robin` (default), `least_conn`, `ip_hash`, weights, `backup` servers.

### Stream (TCP/UDP) proxy

Proxying non-HTTP services such as databases, SSH and game servers. This needs the `stream`
module and a separate `stream {}` context (e.g. `/etc/nginx/streams-enabled/`). Nginx Proxy
Manager has this, and users migrating from it will look for it.

```nginx
stream {
    server {
        listen 5432;
        proxy_pass 10.0.0.20:5432;
    }
}
```

### GeoIP (country) blocking

Requires the `ngx_http_geoip2_module` and a MaxMind database. GoNix should detect the module
first and explain how to install it if it is missing.

### Proxy caching

`proxy_cache_path` (http context) + `proxy_cache` per host or location, with presets for cache
time and bypass rules.

### Bad bot / sensitive path blocking

Toggles to deny common scanner user agents and block paths like `/.git`, `/.env`,
`/wp-admin` (for non-WordPress sites).

```nginx
location ~ /\.(git|env|svn|hg) { deny all; return 404; }
```

## Priority 7 — Automation, migration and teams

- **Export / import** all GoNix-managed state (hosts, lists, presets) to move to a new server.
- **Git-based configuration history:** commit `/etc/nginx` on every successful change, with a
  diff view and "roll back to this commit" in the TUI.
- **Import from Nginx Proxy Manager:** read NPM's database and generate equivalent GoNix hosts.
  This is a strong adoption tool, since many GoNix users come from NPM.
- **Multiple Nginx instances** (already listed in the README).
- **Non-interactive CLI mode.** See the next section; it is the foundation for AI agent support.

## AI agent support ("skills")

### Goal

Let AI agents (Claude Code, other coding/ops agents) manage Nginx through GoNix as easily and
safely as a human does through the TUI. For example: *"Add a host for api.example.com proxying to
port 3000, with HTTPS and the office IP list"*, done in one step and with the same guarantees
(backup, `nginx -t`, rollback, audit log).

An agent cannot drive a TUI reliably. Today its only option is to edit Nginx files by hand, which
bypasses all of GoNix's safety logic. The goal is to give agents a better path than that.

### Proposed approach (in three layers, built in order)

#### Layer 1 — A non-interactive CLI with JSON output (foundation)

Expose the same service layer the TUI uses (`internal/hosts`, `internal/accesslist`, …) as
subcommands. No new business logic: the TUI and the CLI call the same functions.

```bash
gonix host list --json
gonix host show api.example.com --json
gonix host add api.example.com --upstream http://127.0.0.1:3000 --websocket --ssl example.com
gonix host disable api.example.com
gonix iplist create office --allow 192.168.1.0/24 --allow 10.0.0.5
gonix iplist apply office --host api.example.com --location /admin/
gonix cert list --json
gonix nginx test
gonix audit tail --json -n 20
```

Design rules that make it agent-friendly:

- **`--json` on every read command**, with stable, documented fields. Agents parse JSON far more
  reliably than tables.
- **`--dry-run` on every write command**, printing the exact config diff that would be applied.
  An agent (or the human supervising it) can review it before anything changes.
- **Structured errors**: non-zero exit codes and a JSON error object that includes the
  `nginx -t` output when validation fails and rollback happened.
- **Idempotent where possible** (`apply` on an already-applied list is a no-op, not an error).
- **Explicit confirmation for destructive actions** (`host delete` requires `--yes`).
- **Audit attribution**: record the caller, e.g. `actor=cli` / `actor=agent` via an env var
  such as `GONIX_ACTOR`, so humans can see what an agent changed.

This layer is useful on its own for shell scripts, Ansible and CI, so it is worth building
regardless of AI.

#### Layer 2 — A GoNix skill (`SKILL.md`)

Ship an Agent Skill in the repository (e.g. `skills/gonix/SKILL.md`) that teaches an agent how to
use the CLI: the available commands, the recommended workflow, and the safety rules.

```markdown
---
name: gonix
description: Manage Nginx hosts, SSL, access lists and IP lists through the GoNix CLI.
  Use whenever the user asks to add, change, enable/disable or inspect an Nginx site or
  reverse proxy on a server where gonix is installed.
---

# Managing Nginx with GoNix

Never edit files in /etc/nginx directly. Always use `gonix`, which backs up, validates
with `nginx -t` and rolls back on failure.

Workflow:
1. Inspect first: `sudo gonix host list --json`
2. Preview every change with `--dry-run` and show the diff to the user.
3. Apply only after the user agrees.
4. Verify: `sudo gonix host show <domain> --json` and `sudo gonix nginx test`.
...
```

Install it with a single command:

```bash
gonix skill install            # copies SKILL.md into ~/.claude/skills/gonix/
gonix skill install --project  # or into ./.claude/skills/ for one project
```

The skill is just documentation versioned with the binary. `gonix skill install` writes the
copy matching the installed version, so the instructions never drift from the actual CLI.

#### Layer 3 (optional, later) — MCP server

`gonix mcp` would run GoNix as a Model Context Protocol server over stdio, exposing typed tools
(`list_hosts`, `add_host`, `apply_ip_list`, `test_config`, …) with JSON schemas. Benefits over
the skill: typed parameters, no shell quoting, and it works in any MCP-capable client, not only
ones that support skills.

It should only be built if real demand appears, because Layers 1 and 2 already cover most use
cases with much less code. If it is built, it must call the same service layer as the CLI.

### Safety considerations

- GoNix runs as root. An agent should get **read-only commands freely** and **write commands only
  with human approval** (via the agent's permission system, and `--dry-run` first).
- Consider a `gonix --read-only` mode, or a config option that disables write subcommands for
  non-interactive use.
- All agent-made changes go through the same backup/validate/rollback pipeline and show up in the
  audit log with their actor.

### Recommendation

Build **Layer 1 (CLI + JSON + dry-run)** first. It is the real work and is valuable even without
AI. Then add **Layer 2 (SKILL.md + `gonix skill install`)**, which is a small documentation task
once the CLI exists. Leave **Layer 3 (MCP)** until users ask for it.
